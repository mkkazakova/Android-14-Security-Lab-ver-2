# Проверка цифровой подписи APK в Android 14

**Цель** — проверить, какое сообщение показывает системный установщик при первой установке и при двух попытках обновления одного пакета. В обоих обновлениях совпадают версия, манифест и программный код. Меняется подписавший APK ключ.

## Первый запуск

1. Распакуйте ZIP. Перенесите содержимое в корень нового репозитория GitHub, включая скрытую папку `.github`. При использовании Git из каталога распаковки выполните `git add .`, создайте коммит и отправьте его в основную ветку. В корне репозитория должны быть видны `README.md`, `apks/`, `scripts/`, `tests/` и `.github/workflows/signature.yml`.
2. На GitHub откройте **Actions → Android 14 APK Signature → Run workflow** и выберите основную ветку. Если GitHub просит включить Actions, включите их. На компьютере для запуска нужны только браузер и доступ к репозиторию.
3. На странице завершившегося запуска скачайте артефакт **android14-signature-…**, распакуйте и откройте его `README.md` в программе с просмотром Markdown. Под описанием каждого опыта будет фактическое сообщение Android и проверенный снимок, если его удалось получить. `report.json` содержит данные для машинной обработки.
4. Для повтора используйте **Re-run jobs** либо запустите новый workflow. Каждый запуск начинает с чистого AVD и проходит все три этапа последовательно. Выборочная повторная установка версии 2 поверх уже обновлённого пакета изменила бы начальные условия опыта.

## Теоретические сведения

Подпись связывает содержимое APK с ключом подписанта и позволяет обнаружить изменение подписанных данных. Для обновления Android проверяет идентификатор пакета и совместимость подписи с уже установленной версией. В этом опыте оба ключа независимы, ротация ключей не используется. Обычная установка первого APK с ключом A проверяет целостность подписи, но не устанавливает личность разработчика. [Правила обновления Android](https://developer.android.com/google/play/app-updates) · [Проверка подписи APK](https://developer.android.com/tools/apksigner)

| Опыт | Предлагаемый APK | До установки | Ожидаемое состояние после действия |
|---|---|---|---|
| 1.1 | `sample-v1-a.apk`, версия 1, ключ A | Пакет отсутствует | Версия 1, системное окно успеха |
| 1.2 | `sample-v2-b.apk`, версия 2, ключ B | Установлена версия 1 | Окно отказа, прежний APK версии 1 |
| 1.3 | `sample-v2-a.apk`, версия 2, ключ A | Установлена версия 1 | Версия 2, системное окно успеха |

## Эксперимент 1.1 — установка

Files открывает папку Download. Скрипт находит в дереве DocumentsUI файл `sample-v1-a.apk`, нажимает на него и подтверждает установку **Update Sample** в Package Installer. После действия сверяются версия и SHA-256 установленного `base.apk` с исходным файлом.

*Место для системного подтверждения и фактического вывода:* `1.1/result.png` и раздел 1.1 в README артефакта. До запуска результат не установлен.

## Эксперимент 1.2 — отказ при смене сертификата

Не удаляя версию 1, Files открывает `sample-v2-b.apk`. Скрипт ожидает терминальное сообщение установщика. Даже если Android указывает только общий конфликт пакетов, для подтверждения причины требуется запись Package Manager или PackageInstallerSession об ошибке для `ru.securitylab.sample` в журнале **этой попытки**. После отказа проверяются версия 1 и побайтовая идентичность её установленного APK исходному.

*Место для системного отказа и фактического вывода:* `1.2/result.png` и раздел 1.2 в README артефакта. До запуска результат не установлен.

SHA-256 сертификата A — `6f5ca919ff637610ceb5e6c3e8f6cb004b3cd7b729deb3505fc08189937bb87c`. SHA-256 сертификата B — `789bc55715f5138d4fe0c6cd9f11b51ee386fa3bd352222e83a647859c122025`. Свойства входных файлов проверены локально. В CI свежий вызов `apksigner verify --verbose --print-certs` проверяет подпись каждого APK, а `aapt dump badging` извлекает данные манифеста. Обе версии 2 имеют одинаковый набор элементов ZIP с одинаковым распакованным содержимым.

## Эксперимент 1.3 — обновление с исходным сертификатом

Files открывает `sample-v2-a.apk`. Скрипт подтверждает обновление, фиксирует текст результата и проверяет переход с версии 1 на версию 2 и SHA-256 нового установленного APK. Система может показать тот же текст, что и при первой установке. Для третьего опыта эмулятор переводится в альбомную ориентацию перед открытием файла. Признаком обновления служит смена установленной версии.

*Место для системного подтверждения и фактического вывода:* `1.3/result.png` и раздел 1.3 в README артефакта. До запуска результат не установлен.

## Как формируются доказательства

- Используется Ubuntu 24.04, доступ к /dev/kvm, Android 14 Google APIs x86_64, Pixel 2, стандартная английская локаль образа. Эмулятор проверяется на готовность Package Manager и API 34. APK берутся из `evidence/raw-standard/apk/` предоставленного отчёта. Закрытые ключи, Gradle и сборка приложений для запуска не требуются.
- Каталог открывается через `ACTION_VIEW` с URI провайдера внешнего хранилища. Если прямой переход не удался, скрипт открывает корень хранилища в Files и выбирает Download. Затем **сам Files** открывает выбранный APK. Разрешение неизвестного источника на лабораторном AVD предварительно настраивается для системного источника. При появлении предупреждения со ссылкой на настройки скрипт обрабатывает переключатель «Allow from this source». [Манифест DocumentsUI Android 14](https://android.googlesource.com/platform/packages/apps/DocumentsUI/+/refs/heads/android14-platform-release/AndroidManifest.xml)
- Вместо фиксированных координат используются границы элементов из свежего XML. Скрипт проверяет владельца элементов, заголовок приложения, сообщение и кнопку завершения. Пока окно открыто, захватывает `adb exec-out screencap -p`. При неудаче повторяет захват, затем пробует штатную команду консоли эмулятора `adb emu screenrecord screenshot` с теми же проверками. Повторно считывает дерево после снимка и сопоставляет состояние и границы сообщения. Проверяет PNG, декодирование пикселей, контраст области сообщения, SHA-256 и отсутствие побайтовых дубликатов. Файл сохраняется без обработки. Экран тестового приложения в сценарии не открывается.
- `PASS` требует совпадения ожидаемого исхода, подтверждения состояния пакета и сохранения проверенного PNG. `FAIL` фиксирует наблюдаемый противоположный исход или противоречие со штатным состоянием пакета. `INCONCLUSIVE` означает нехватку доказательств, в том числе при неподтверждённой причине отказа. В этих двух случаях job завершается ошибкой, а артефакт сохраняется. Технический результат, окно и снимок отражаются отдельно.
- Для разбора откройте `report.json`, затем `1.x/latest.xml`, `terminal.xml` и `logcat.txt` соответствующего этапа. Если окно не распознано, скрипт сохраняет последние доступные XML, список окон и активностей в каталоге этапа. Полные выводы SDK находятся в `inputs/`. Свойства образа, включая build fingerprint, находятся в `device.txt`. При ошибке до старта эмулятора смотрите отчёт и журнал job. XML может отсутствовать при недоступности UI Automator.

## Общий вывод и границы проверки

До первого запуска GitHub Actions достоверно установлены свойства тестовых APK. В прежнем проекте Python-скрипт устанавливал пакет через ADB и вызывал Activity образца после каждой операции. Старый отчёт сохранил ошибку несовместимости, но SHA-256 первых двух снимков одинаков. Поэтому старые изображения не используются как доказательства нового опыта.

Новый запуск формирует вывод по трём наблюдениям в README артефакта. Набор системных приложений и вид диалогов зависят от ревизии образа. Если системный интерфейс не отдаёт сообщение в XML или его область скрыта при захвате, визуальное подтверждение остаётся открытым. Для приёмки откройте три PNG из **одного запуска**, прочитайте реальные сообщения и сопоставьте второй снимок с записью о несовместимости, а третий — со сменой версии в `report.json`.
